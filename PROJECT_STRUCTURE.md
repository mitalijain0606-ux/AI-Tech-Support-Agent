# Operon — Project Structure

## The architecture, in one paragraph

One backend and one extension **source**, both target-agnostic — neither
knows or contains any reference to a specific customer's site. Each customer
(or each demo) gets its own **built** extension package, generated from that
shared source, with its permissions locked to exactly one domain. Nothing
is shared at runtime between two built packages; only the source and the
backend are reused. That reuse is what proves the product generalizes;
the per-target lockdown is what makes each deployed copy safe to hand to a
customer.

## Phasing

- **Phase 1 (now):** backend + the `github` target, working end-to-end
  against real github.com.
- **Phase 2 (later, after Phase 1 is solid):** a small fake SaaS app we
  build ourselves (4-5 screens, 5+ seeded bugs) + its own `fake-saas`
  target build, proving the same core works on a product we control too.

## What "production-grade" means here

Real infrastructure around the same small Phase-1 file set — typed config,
tests, a real build — not deeper folders for features that don't exist yet.
`providers/`, `agent/` (five-stage pipeline), `realtime/`, `models/` are all
real future work, but adding them empty now would be scaffolding, not
production quality. They get created when there's a second provider, a
database, or five distinct pipeline stages to actually justify the split.

## Folder structure

```text
operon/
├── README.md
├── PROJECT_STRUCTURE.md                # this file
│
├── backend/                            # FastAPI — stateless, target-agnostic
│   ├── pyproject.toml                  # package metadata, deps, ruff + pytest config
│   ├── requirements.txt                # pinned, for Vercel's Python builder
│   ├── .env.example                    # GROQ_API_KEY, GROQ_MODEL — documented, not committed
│   ├── vercel.json
│   ├── api/
│   │   └── index.py                    # entry point Vercel's Python runtime serves
│   ├── operon_backend/                 # real installable package (not a generic "app")
│   │   ├── __init__.py
│   │   ├── main.py                     # FastAPI app factory: /health, /api/diagnose, /api/policy
│   │   ├── config.py                   # typed Settings (pydantic-settings), reads env once
│   │   ├── schemas.py                  # EvidenceBundle + sub-schemas (Contract 1)
│   │   ├── tripwire.py                 # server-side credential scanner (Contract 1a)
│   │   ├── policy.py                   # closed action enum + evaluate() (Contract 3)
│   │   └── llm.py                      # Groq call: classify + diagnose + plan
│   └── tests/
│       ├── conftest.py
│       ├── test_tripwire.py            # the credential-tripwire test — write this one first
│       ├── test_policy.py
│       └── test_llm.py
│
└── extension/                          # MV3 — ONE shared source, TypeScript, no domain hardcoded
    ├── package.json
    ├── tsconfig.json
    ├── src/
    │   ├── background.ts               # service worker: debugger attach, evidence assembly,
    │   │                               #   calls backend, executes approved actions
    │   ├── content.ts                  # DOM skeleton + storage-shape reader
    │   └── popup/
    │       ├── popup.html              # seed bug / ask Operon / approve UI
    │       └── popup.ts
    │
    ├── manifest.template.json          # base manifest; host_permissions/matches left as a
    │                                   #   placeholder the build step fills in
    ├── targets/                        # per-customer / per-demo configuration
    │   ├── github.json                 # ✅ Phase 1 — { "domain": "github.com" }
    │   └── fake-saas.json              # ⏳ Phase 2 — domain TBD once the app exists
    │
    ├── scripts/
    │   └── build.mjs                   # esbuild: bundles src/*.ts, stamps manifest.template.json
    │                                   #   with one target's domain, writes dist/<target>/
    │
    └── dist/                           # build output — one loadable folder per target,
        ├── github/                     #   gitignored, regenerated by `npm run build -- github`
        │   └── manifest.json           # host_permissions locked to github.com only
        └── fake-saas/                  # ⏳ Phase 2 — doesn't exist until build.mjs runs for it
            └── manifest.json

(Phase 2 only, later)
└── fake-saas-app/                      # the small demo SaaS product itself
    └── ...                             # scope TBD when Phase 1 is done
```

## What's intentionally not here yet

- No database, no Redis, no session persistence — Phase 1's backend is
  stateless by design; the extension carries context between calls.
- No `packages/operon-core` shared package — there's only one consumer
  (the extension) so there's nothing to share yet.
- No `providers/`, `agent/`, `realtime/` — these become real once there's a
  second provider (an SDK), a database, or enough pipeline stages to split
  out, not before.
- No `fake-saas-app/` content — Phase 2 doesn't start until Phase 1 works
  end-to-end on github.com, per the agreed sequencing.
